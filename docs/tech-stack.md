# 技術選定

このアプリで使う技術と、それを選んだ理由をまとめます。
「チームで決めたこと」と「テックリードの提案（チームで確認して確定する）」を分けて書いています。

## 選定の方針

1. **全員がスクールで学習中の技術を土台にする**（2週間で新しいことを覚える時間は少ない）
2. **Rails の標準（デフォルト）に乗る**。標準から外れるほど、調べても情報が見つからず、AI の回答もぶれやすくなる
3. **パソコンにインストールするものを減らす**（Docker と Git があれば開発できる状態にする）
4. **無料で動かせる**
5. **講師から共有された参考リポジトリ（hisaju/task-breakdown）と揃えられるものは揃える**。設定ファイルや手順をそのまま参考にでき、詰まったときに比較できる

## 1. チームで決めたこと

| 技術 | 選んだ理由 |
|---|---|
| **Ruby on Rails** | 全員がスクールで学習中。画面・DB・テストまで1つのフレームワークで作れ、4人が同じ書き方で開発できる |
| **Docker（Docker Compose）** | 全員がスクールで学習中。Mac / Windows の違いや Ruby のバージョン違いによる「自分のパソコンだけ動かない」を防げる |
| **Tailwind CSS** | 実際の開発現場でよく使われており、経験してみたい。画面のモック（`mock/mock.html`）の見た目も、Tailwind のクラスで再現できる |

## 2. テックリードの提案（未確定）

### 言語・フレームワーク

| 区分 | 提案 | 理由 | 検討した他の候補 |
|---|---|---|---|
| Ruby / Rails のバージョン | **Ruby 3.4 / Rails 8.1** | 現時点の最新の安定版で、参考リポジトリと同じ。スクールのカリキュラムは Rails 7 系と 8 系を選べるが、これから学ぶなら最新のほうが長く役立つ。Docker で動かすので、パソコンの Ruby のバージョンは関係ない | Rails 7 系：カリキュラムで選べるが、参考リポジトリの設定をそのまま使えなくなり、Rails 8 標準の機能（認証の生成、Solid Queue など）も使えない |
| 画面の動き | **Hotwire（Turbo・Stimulus）** | Rails の標準。モックにある動き（マニュアルの確認、レベルの自己申告・承認、研修の「教え終わった」）は、サーバーで HTML を作り直して差し替えるだけで実現できる。研修画面の下書き（「変更を保存」まで DB に入れない）は Stimulus で持つ | React / Vue：API と画面を別々に作る必要があり、2週間では重い |
| JavaScript の読み込み | **importmap** | Rails の標準。Node.js（npm）が不要になり、Docker のイメージも軽くなる | jsbundling / Vite：npm のライブラリをたくさん使うときに必要。今回は不要 |
| CSS | **Tailwind CSS v4（tailwindcss-rails）** | Node.js なしで Tailwind をビルドできる Rails 公式の gem | — |
| UI 部品 | **ライブラリは使わない**（Tailwind CSS ＋ `@layer components`） | モックは UI 部品ライブラリを使わず、独自の CSS で書かれている。モックの見た目をそのまま再現するため、モックで直接書かれた style は Tailwind のクラスに、繰り返し使う部品（ボタン・バッジ・カードなど）は `application.css` の `@layer components` に、色は `@theme` のデザイントークンに移す | daisyUI v5：当初のモック（`mock/old/`）で使っていたが、いまのモックは使っていない。入れると、モックにない daisyUI の既定の見た目を打ち消す手間が増える |

### データベース

| 提案 | 理由 | 検討した他の候補 |
|---|---|---|
| **PostgreSQL 17** | 無料で使えるクラウドの DB（Neon など）やデプロイ先が PostgreSQL に対応しており、開発と本番で同じ DB を使える。参考リポジトリと同じ | SQLite（Rails 8 の標準）：手軽だが、無料のデプロイ先ではサーバーが再起動するとデータが消えることが多い。MySQL：スクールで使っていれば候補だが、無料のクラウド DB の選択肢が少ない |

### テスト・品質

| 区分 | 提案 | 理由 | 検討した他の候補 |
|---|---|---|---|
| テスト | **RSpec ＋ FactoryBot** | スクールのカリキュラムで学ぶのが RSpec。日本の Rails の現場でも最も使われており、参考リポジトリとも同じ | Minitest（Rails の標準）：Rails に最初から入っているが、スクールで学ぶものと違う |
| 画面テスト | Capybara（主要な流れ1本だけ） | 画面操作のテストは書くのも直すのも時間がかかるので、最小限にする | — |
| コードの書き方チェック | **RuboCop（rubocop-rails-omakase ＋ rubocop-rspec）** | Rails 標準の設定。書き方が揃い、レビューで書き方の指摘をしなくて済む | — |
| セキュリティ診断 | **Brakeman / bundler-audit / importmap audit** | Rails 8 で最初から入っている。無料で、CI で自動実行できる | — |
| CI | **GitHub Actions** | Rails 8 が設定ファイルを最初から作ってくれる。GitHub で PR ごとに自動でテストとチェックが走る | — |

### 認証・その他

| 区分 | 提案 | 理由 |
|---|---|---|
| ログイン | **MVP では作らない**。ヘッダーの「操作する人」で選んだユーザーをセッションに保存する | モックにもログイン画面がない。デモで管理者とスタッフ5人を切り替えて見せやすい。必要になったら、Rails 8 標準の認証機能（`bin/rails generate authentication`）を使う（Devise より仕組みが見えやすく、参考リポジトリと同じ） |
| 日本語化 | **rails-i18n**、`time_zone = "Tokyo"`、`default_locale = :ja` | エラーメッセージや日付を日本語・日本時間で表示する |

### デプロイ（本番環境）

| 提案 | 理由 | 検討した他の候補 |
|---|---|---|
| **Render（アプリ）＋ Neon（PostgreSQL）**（要確認） | 参考リポジトリと同じ構成。GitHub と連携して、main にマージすると自動でデプロイされる。どちらも無料プランがある | Heroku：手順は簡単だが有料。Fly.io：CLI 操作が多い。Kamal（Rails 8 の標準）：自分でサーバーを用意する必要があり、2週間では重い |

- 無料プランの制限（しばらくアクセスがないと停止する、DB の容量や期限など）は、雛形作成時に最新の情報を確認します
- **デプロイは最初の土台づくり（M1）の中で済ませます**。最後にまとめてやると高い確率で詰まるためです

### 開発ツール

| 区分 | 提案 | 理由 |
|---|---|---|
| AI 開発ツールのルール | **`AGENTS.md` に共通ルールをまとめる**。Claude Code 用の `CLAUDE.md` は `AGENTS.md` を読み込むだけにする | メンバーが使うのは Claude Code と Codex。Codex は `AGENTS.md` を、Claude Code は `CLAUDE.md` を自動で読むので、ルールを1か所に書けば両方が同じルールで開発できる |
